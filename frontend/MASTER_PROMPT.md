═══════════════════════════════════════════════════════════ LOCKED TECHNICAL DECISIONS (confirmed from codebase — never reverse these without explicit confirmation) ═══════════════════════════════════════════════════════════
Stack: React 18 + Vite + PocketBase + TanStack Query + Zustand + Tailwind + Leaflet — do not suggest migrating to Supabase/ Firebase, Redux, or a different map library (react-leaflet is already installed and wired into LiveMapPage and GeofencePage)
ft_ namespace — never touch bs_* (SalesTrack) or any other namespace on the shared fieldtrack-kenya.fly.dev instance
Multi-tenant via ft_org_members: a user's org_id is NOT stored directly on ft_users — it is resolved at login by querying ft_org_members for user_id = "<id>" && is_active = true and cached onto the in-memory user object (see store/auth.js hydrateUser()/fetchOrgId()). ANY new query that needs org scoping must go through user.org_id from useAuth(), never assume ft_users has an org_id field directly.
Roles (ft_users.role): admin, manager, supervisor, field_staff. isAdmin() = admin|manager. isSupervisor() = admin|manager| supervisor (this is the "can see admin pages" gate used by App.jsx's <Guard adminOnly>). isField() = field_staff only. NEVER invent a 5th role without updating all three helper functions in store/auth.js and every place that branches on them.
Offline-first via IndexedDB (src/lib/offlineQueue.js, DB name "fieldtrack-offline"), NOT Dexie (that's the sister SalesTrack project's choice) — raw IndexedDB with typed enqueue helpers (enqueueOrder, enqueueExpense, enqueueFarmerVisit, enqueueAttendanceClockIn/Out). Any new offline-capable write must add its own typed enqueueX() helper here, never call the generic enqueue() directly from a page component.
GPS tracking is battery-optimised and adaptive (src/hooks/ useGPS.js): pings every 60s while moving (speed > 0.8 m/s), every 5 minutes while still, drops readings with accuracy worse than 80m, and re-checks geofence zones every 3rd ping (not every ping) to save battery. This is ALSO a market differentiator (see COMPETITIVE INTELLIGENCE — Repsly users report battery-draining GPS) — never change these intervals without understanding both the battery-vs-freshness tradeoff AND the competitive positioning being deliberately protected here.
GPS consent is explicit and persisted to localStorage (fieldtrack_gps_consent) as null/true/false — tracking must NEVER silently auto-start on a null (undecided) consent state. This is a legal/trust requirement, not just a UX nicety — field agents are being tracked all day, they must affirmatively agree.
Geofencing math lives in src/lib/geofence.js (haversineDistance, isInsideZone, checkGeofences) — pure functions, zero PocketBase calls. Reuse these, never reimplement distance math inline elsewhere (e.g. in LiveMapPage or reports).
Orders go through a formal approval chain: draft → pending_approval → approved | rejected | revision_requested. Field staff can never self-approve. Rejections REQUIRE a reason of at least 10 characters (enforced client-side in useRejectOrder — do not remove this validation, it exists so rejected reps get an actionable reason, not a bare "no").
Order payments are a SEPARATE approval chain from orders themselves (ft_order_payments, status pending → approved), because a field agent recording "customer paid" is a claim that needs verification before it counts toward collections — never let a payment auto-approve on creation, and never let it count toward useOrderPaymentSummary's totalPaid until status=approved.
TanStack Query is the ONLY data-fetching pattern — every list/ detail view is a useQuery, every write is a useMutation with onSuccess invalidating the relevant queryKeys. Never fetch data in a bare useEffect + useState when a query hook already exists or could be added to the relevant hooks/useX.js file.
Realtime updates use PocketBase's native .subscribe("*", cb) (see useOrdersRealtime in hooks/useOrders.js and hooks/useRealtimeSync.js) combined with TanStack Query's invalidateQueries — this is the pattern for anything that needs to feel "live." Several list queries additionally poll via refetchInterval (5-60s depending on urgency) as a redundant safety net in case a subscription drops — keep both mechanisms, don't remove polling just because a subscription exists.
Notifications are a first-class PocketBase collection (ft_notifications), not a toast-only pattern — every meaningful business event writes a persistent notification record IN ADDITION to any toast. This powers the in-app notification center (src/store/notifications.js) and must never be skipped "because a toast already showed."
Currency: KES only, formatted via formatKES() from hooks/useOrders.js (KES ${Number(amount).toLocaleString('en-KE')}) — reuse this helper everywhere money is displayed.
Customer categories (ft_customers.category and ft_orders.customer_category): distributor, stockist, agrovet, farmer — exactly these 4, exported as CUSTOMER_CATEGORIES from hooks/useOrders.js. Never add a 5th category without updating targets, reports, and the PocketBase enum together.
Payment methods (ft_order_payments.payment_method): mpesa, cash, cheque, bank_transfer — exported as PAYMENT_METHODS from hooks/useOrderPayments.js.
SOS emergency alert types: medical, security, accident, breakdown, robbery, other — a field agent holds a button for 3 seconds (HOLD_DURATION) to send GPS coordinates + alert type to ft_sos_alerts with status "active". Safety-critical — never make the hold shorter, never gate SOS behind the offline-queue/ approval-queue pattern used elsewhere.
No animation libraries — pure CSS/Tailwind transitions only, same performance-budget philosophy as the sister SalesTrack project (low-end Android phones, unreliable data).
